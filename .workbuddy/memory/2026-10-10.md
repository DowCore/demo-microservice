## 追加：登录 ID2052 事故修复（同日，用户报障）

**用户报障**：前端跳登录变成 `error: invalid_request / The specified 'client_id' is invalid. / ID2052`。

**根因（已用数据坐实）**：我在 §8.5.3 的密钥治理里把 DbMigrator 的 `ClientSecret` 抽到
`appsettings.secrets.json`，但那里用**同一个 `"Clients"` 键**又写了一份数组。**.NET 配置对数组是按索引合并**
（不是替换、不是拼接），于是与 `appsettings.json` 同索引条目**逐字段混血**：
索引 0 的 `MetaDow_Vue` 被改成 `Administration_API`（却保留 Vue 的 GrantTypes/Scopes/RedirectUris）…
`MetaDow_Vue` 不再是任何条目的 ClientId ⇒ `RemoveObsoleteClientsAsync` 把它**软删除**。
MongoDB 实测：`IsDeleted: true`，`DeletionTime: 2026-10-10T13:33:09.713Z`；`Administration_API` 的
`RedirectUris` 里混进了 `http://localhost:5666/auth/oidc-callback`，`Permissions` 混进了
`gt:password`/`gt:refresh_token`/`scp:MetaDowAuthServer` —— 与推断完全一致。

**关键事实（以后省时间）**：
- OpenIddict 的 applications/scopes/tokens 落在 **`MetaDowIdentityServiceDb`**（`AbpDbConnectionOptions`
  把 `AbpOpenIddict` 映射到 `IdentityServiceDb`），不在独立 AuthServer 库；AppHost 也没建 AuthServerDb。
- Mongo 容器凭据在 `docker inspect` 的 `MONGO_INITDB_ROOT_USERNAME/PASSWORD`；容器名形如 `mongodb-<hash>`，
  端口是随机映射（本次 127.0.0.1:64871）。
- ABP MongoDB 的实体字段是 **PascalCase**（`ClientId`/`IsDeleted`/`RedirectUris`…），`Permissions` 等集合
  在库里存的是 **JSON 字符串**而非内嵌数组。

**修复**（5 处代码/配置 + 1 次数据修复 + 1 条护栏）：
1. `DbMigrator/appsettings.secrets.json`(+`.example`)：密钥改放**独立对象键 `ClientSecrets:{clientId}`**（对象按 key 合并，安全）。
2. `OpenIddictDataSeeder`：新增 `LoadClients()` 合并密钥；新增 `ValidateClients()` **先校验再碰库**；
   `PruneObsoleteClients` **显式开关**（默认 false，逐个打 Warning）；`ApplyClientSettings` 改**配置即事实**
   （先 `Clear()` permissions/requirements/redirects 再重建 ⇒ 重跑迁移可自愈收敛，原实现只加不减，混血永不清除）。
3. 数据修复脚本：恢复软删的 `MetaDow_Vue` + 把 4 个 API 客户端的 ClientUri/Redirect/PostLogout/Permissions
   收敛回配置；修复后 5 个客户端全部 `IsDeleted:false` 且无串味。
4. 新增护栏 `tests/.../SecretsConfigSafetyTests.cs`：扫全仓 `appsettings*.secrets.json*`（含 `.example`）
   **禁止任何 JSON 数组**并打印 JSON 路径；已用探针文件验证会真失败（非空跑）。
5. 文档：`lowcode-form-oa-enhancement.md` 新增 **§8.6 事故复盘**；`src/CLAUDE.md` 写死「secrets 文件禁止数组」
   规则 + Troubleshooting 增 ID2052 排查路径（含"去 Identity 库查 OpenIddictApplications"）。

**验证**：`curl -k https://localhost:7600/connect/authorize?client_id=MetaDow_Vue&...` 由错误响应恢复为
`302 → /Account/Login`（**未重启 AuthServer**，说明负缓存没有跨请求留存）；`dotnet build Meta.Dow.slnx -c Release` 0 错误；

### 【第二起登录事故】网关把 JWT 受众写死成解决方案名 → 有效令牌全线 401

**现象**：登录页能打开、登录成功取到令牌（库中可见），但随后控制台刷屏 401，页面弹
`未认证或令牌无效` + `页面加载失败：Request failed with status code 401`。

**根因**：8.5「网关加固」写了 `options.Audience = "Meta.Dow"` + `ValidateAudience = true`。
但 OpenIddict 把**「作用域关联的资源名」**写进令牌 `aud`；本仓 `OpenIddictScopes.Resources`
与 `DbMigrator/appsettings.json` 一致声明四个作用域各自 `Resources=[自身名]`：
`MetaDowAdministration / MetaDowAuthServer / MetaDowIdentityService / MetaDowSaaS`。
前端（`MetaDow_Vue`）申请 scope = `openid profile email offline_access MetaDowIdentityService
MetaDowAdministration MetaDowSaaS` ⇒ 令牌 `aud` **永远不含 `Meta.Dow`** ⇒ 每个有效令牌都被判无效。
（`MetaDowAuthServerModule` 的 `AddAudiences("Meta.Dow")` 是 AuthServer **自身**的"可接受受众"声明，
不会写进签发令牌——两者极易混淆。）

**为何现在才暴露**：前端 `/api/menu/*`、`/api/permission-management/*` 原先**无显式路由**，
落进 8.5 新增的 `administration-fallback`（`{**catch-all}` + 需认证）；登录成功后前端第一件事就是拉
`/api/menu/all`（`.env` `VITE_GLOB_API_URL` 为空 → `/api` 由 Vite 代理到网关 7500），必然撞上。

**修复**（`src/gateway/Meta.Dow.Gateway/`）：
1. `Program.cs`：**不再写死单一受众**。默认 `ValidateAudience = false`（仍校验签名/签发者/有效期）；
   如需网关强校验，用 `AuthServer:ValidAudiences`（数组）显式列出**全部**允许受众。
2. `appsettings.json`：`AuthServer.Audience` → `AuthServer.ValidAudiences: []`；并补两条前端在用却缺路由的
   `menu`、`permission-management` → administration 集群。

**真机验证**（只读探测）：令牌 `aud=['MetaDowAdministration','MetaDowIdentityService','MetaDowSaaS']`；
经网关 7500 —— `/api/menu/all` 带令牌 **200**（原 401）、`/api/abp/application-configuration` **200**、
`/api/permission-management/permissions` **200**、`/api/account/my-profile` **200**；无令牌仍 **401**（正确）。
文档：`lowcode-form-oa-enhancement.md` §8.7 + §8.7.1。

**另**：控制台 `[Vben Form] BREAKING CHANGE ... slotProps.componentProps` 是**上游模板自带 Vite 插件
无条件注入**（`internal/vite-config/src/plugins/form-field-slot-migration-warning.ts`，`apply:'serve'`，
启动 logger.warn + transformIndexHtml 注脚本），不扫代码。本仓 app 代码零 `v-bind="slotProps"`，
框架 `createFieldSlotScope()` 已提供 `componentProps`。**非缺陷，无需整改**；嫌吵可在
`internal/vite-config/src/plugins/index.ts:150` 摘掉插件注册。

**教训（操作纪律）**：**不要 `docker rm -f` "看起来是孤儿"的容器**。我误删了你正在服务的
MongoDB/Redis（它们的数据在命名卷，重启即恢复，但服务会瞬断并报 Mongo 超时）。
任何时候清理容器前必须先确认**没有任何在跑的 AppHost/服务在依赖它**，并且**用户没在用**。
默认动作应是"不动"，而非"先清干净再重建"。

**长期规则**：**同时前置多个 API 的网关，不要在网关写死单一 JWT 受众**；受众是"每个 API 自己的事"，
网关只做签名/签发者/有效期把关。要校验必须列全。

## Aspire Dashboard 启动告警 `The payload was invalid`（2026-10-10，结论：非缺陷、非我的改动）

**现象**：启 AppHost 时 `Aspire.Hosting.Dashboard.Model.BrowserStorage.LocalBrowserStorage[0]` 报
`Error when reading 'Aspire_Resources_CollapsedResourceNames_MetaDow' as List`1` +
`CryptographicException: The payload was invalid`（栈：`CbcAuthenticatedEncryptor.DecryptImpl`）。

**定性**：`Aspire.Hosting.Dashboard` = **内嵌在 AppHost 进程里的控制台**（不是业务 Host）。
它用 `ProtectedBrowserStorage` 把「资源分组折叠状态」这类 **UI 偏好**加密后写浏览器 localStorage。
Data Protection 是 AES-CBC+HMAC **认证加密**，HMAC 不过即抛 `payload was invalid`。

**机制（确定）**：两种可能——① 加密用的 DP key 不在当前环里；② **ApplicationDiscriminator 变了**（官方：
"The discriminator value is **implicitly included in all protected payloads**"）。默认 discriminator=ContentRootPath。

**本机取证（关键）**：密钥环在 `%LOCALAPPDATA%\ASP.NET\DataProtection-Keys`，7 个 key，**连 2024-03 的都在**，
最新 key 2026-09-09 创建、有效至 2026-12-08（未过期）⇒ **密钥环稳定、没被清理** ⇒ 失败不是"密钥被删"，
而是**加密时的 discriminator/用途与当前实例不同**（典型：Aspire 升级前后 / 仓库路径变更 / 浏览器数据来自别处）。

**排除我的责任（有据）**：`git diff HEAD -- src/apps/Meta.Dow.AppHost` 唯一的改动是 CPM 把 `Version` 属性
挪进 `Directory.Packages.props`；`Aspire.AppHost.Sdk/13.5.3` 与 4 个 `Aspire.Hosting.* 13.5.3` **版本未变**。

**已做**：AppHost 两个 `appsettings*.json` 的 `Logging:LogLevel` 加
`"Aspire.Hosting.Dashboard.Model.BrowserStorage": "Error"`（**只压这一类被 Aspire catch 掉的 warning，Error 照打**）。
真正的消除办法在浏览器侧：控制台页面 F12 执行
`Object.keys(localStorage).filter(k=>k.startsWith('Aspire_')).forEach(k=>localStorage.removeItem(k))`。

**长期规则**：**不要**为了消这个告警去删 `%LOCALAPPDATA%\ASP.NET\DataProtection-Keys`——它是**机器级共享**的，
业务服务开发态 DP 也用它，删了会让所有服务重新生成密钥、丢失既有保护负载。文档见 §8.8。

## 表单设计器「容器删不掉」修复（2026-10-10，前端 `vue-demo`）

**现象**：VForm 设计器里选中「栅格列」后没有任何删除入口；误拖的栅格/表格/标签页也删不掉，
只能「清空」整表。（截图右栏显示 `格宽度 span/左侧间隔/右移栅格…` ⇒ 选中对象是 **`grid-col`**。）

**根因（4 处）**
1. `vform-node.vue` 操作条条件 `selected && !widget.internal`，而 `grid-col`/`table-cell`/`tab-pane`
   在 `vform-model.ts` 里都 `internal: true` ⇒ 这三类容器**永远没有操作条**（且它们由父容器直接渲染，
   根本不走 `VFormNode`，所以 `!widget.internal` 这个判断本身就是空转）。
2. `vform-designer.vue` 属性面板「移除组件」也被 `v-if="!selected.internal"` 挡掉。
3. **更根本**：容器选不中。`.vf-col`/`.vf-cell`/`.vf-pane` 的 `@click` 都 `stopPropagation` 后选中自己，
   `<Tabs>` 还整块 `@click.stop` ⇒ 栅格/表格/标签页的父容器几乎无可点区域。
4. `removeWidget` 是纯递归删除 ⇒ 直接删内部单元格会留 **0 列栅格 / 0 页签 / 缺格表格** 的空壳，
   空壳渲染不出可点面，画布上再也选不中。

**修复**
- 容器节点左上角加**容器抓手**角标（栅格/表格/标签页/卡片/子表单/树形），点它选中容器本身。
- 选中的栅格列/表格单元格/标签页**内联红色「删除」**。
- 属性面板去掉 `v-if="!selected.internal"`。
- `vform-model.ts` 新增 `findParentWidget()` + `removeWidgetSafe()`：删最后一列/最后一页签/表格最后一列时
  **连整个容器一并删**；`removeSelected` 改用它。

**验证（真机 Chrome + playwright-core，只读交互未保存）**：A 删栅格列、B 删整个栅格容器、C 面板移除 ——
11 项断言全绿，控制台 0 错误；`pnpm -F @vben/web-antd run typecheck` exit 0。文档 §8.9。

**改动文件（全部在 `D:/Project/vue-demo/apps/web-antd/src/views/orchestration/shared/`）**：
`vform-node.vue`、`vform-designer.vue`、`vform-model.ts`。
