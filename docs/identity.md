# 身份、权限与菜单

功能授权沿用 ABP 开源的 Identity 和 PermissionManagement：先定义权限，再授给角色或用户，菜单只引用权限名。对标的是这条路径，不引入 ABP 商业版模块。

证据在 [身份契约](./detail/identity-contract.md) §2、§4、§8。基线 `267d375`。

## 已实现

- 用户、角色、权限授予。
- 组织机构为自研服务，审批流的「主管」使用这棵组织树。
- 动态菜单 `SysMenu`：服务端按权限过滤，子节点可见时补全父目录，按钮类型不进侧栏。
- 多租户开启。菜单和数据范围配置都带 `TenantId`。
- 数据范围有五种，并能解析当前用户「我的」范围。解析结果目前只从接口回传。

## 相对对标的不足

| 对标有的 | 本仓现状 |
|---|---|
| 行级数据权限作用在列表查询上 | `ApplyDataPermission` 没有业务调用点。配了数据范围，列表行数不变 |
| 超管豁免可配置 | 角色名 `admin` 在看菜单和数据范围时恒为全部，配成「仅自己」也不生效 |
| 租户管理员初始口令不可预测 | 新租户回退到公开默认口令 |
| 生产环境不记录个人身份信息 | `ShowPII` 在各宿主上打开 |
| 服务之间通过 HTTP 客户端调用 | 客户端项目存在，没有宿主引用。服务之间靠共享 Mongo |

部门及子部门的匹配是字符串前缀，不是按组织树边界。资源名是自由字符串，没有白名单。

## 后续规划

| 优先级 | 事项 |
|---|---|
| P1 | 业务查询接入 `ApplyDataPermission`。配成「仅自己」后，列表行数必须下降，并有测试 |
| P1 | 去掉按角色名硬编码的 `admin` 豁免，菜单和数据范围用同一种判定 |
| P1 | 新租户管理员使用随机口令，去掉公开回退值 |
| P1 | `ShowPII` 只在开发环境开启 |
| P2 | 数据范围的资源名改为白名单；部门及子部门按组织树展开 |
| P2 | 隐藏菜单若仍注册路由，前端守卫要再查一次功能权限 |

明确不做：另建「角色 ↔ 菜单」授权表。看不见菜单不等于可以跳过 API 上的权限特性。
