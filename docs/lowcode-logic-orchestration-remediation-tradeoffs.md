# 逻辑编排补齐：实现前的能力取舍对比

> 编制日期：2026-10-13
> 配套：《Meta.Dow-逻辑编排补齐实施方案-2026-10-13.md》（本文是其前置的取舍论证）
> 目的：**每项改动落地前，先比对"现有实现 vs 主流参考"，明确抄什么、避什么，防止照搬造成倒退。**

---

## 总原则（三条，贯穿全部实现项）

| 原则 | 含义 | 反面（要避免的） |
|---|---|---|
| **① 复用优先于新建** | 平台已有基建一律接线，不重造 | 为每个执行器各写一套重试；新建一套事务机制 |
| **② 静默零容忍** | 配置被接受就必须生效；不生效就在发布前报错 | 保留 `TimeoutMs` 这种"配了不生效"的字段 |
| **③ 借纪律不借形态** | 抄 Temporal/n8n 的"每条外部副作用都有护栏"，不抄它们的 worker 集群/连接器生态 | 引入工作流引擎、引入分布式执行 |

---

## R1　HTTP 重试：现有 vs 主流

| | 现有实现 | 主流参考（n8n / Temporal） |
|---|---|---|
| 机制 | `AddStandardResilienceHandler()` 全局注册（`ServiceDefaults`） | n8n 节点级 `retryOnFail`；Temporal Activity 级 `RetryPolicy` |
| 粒度 | **全局一份**，所有 HttpClient 共用 | **节点级 / Activity 级**，可逐个配置 |
| 对非幂等方法 | **默认重试**（危险） | n8n 需显式开启；Temporal 要求声明幂等 |
| 熔断 | 有（标准处理器自带） | n8n 弱；Temporal 靠 Activity 重试策略 |

**取舍**：
- **抄主流**：非幂等方法**默认不重试**（Temporal/n8n 的一致立场）。→ 调 `DisableForUnsafeHttpMethods()`。
- **守现有**：保留全局注册（本系统只有"HTTP 出站"一类外呼，全局一致比逐节点配置更省心；且它已带来熔断，成本为零）。
- **不抄**：不做节点级 `retry` DSL 字段。理由：全局策略 + 安全默认值已覆盖 90% 场景，而新增 DSL 字段意味着**校验、前端面板、契约同步、种子、测试**六处联动（见方案 §6 验收模板）——**投产比不成立**。真需要时再作为独立项。

> **一句话**：这项是"把已有能力的默认值调安全"，不是"加能力"。改动量 = 1 个方法调用 + 1 处超时对齐。

## R2　节点级超时：现有 vs 主流

| | 现有实现 | 主流参考 |
|---|---|---|
| 字段 | `TimeoutMs`（`:223`）/ `BranchTimeoutMs`（`:376`）/ 分支 `TimeoutMs`（`:492`）**已定义** | LiteFlow `WHEN` 的 `maxWaitSeconds`；n8n 节点超时；Temporal `StartToCloseTimeout` |
| 消费 | **零消费**（声明即弃） | 全部生效 |
| 默认 | 无（只有 HttpClient 的 30s 全局） | n8n 无默认（不限）；Temporal 必须显式声明 |

**取舍**：
- **抄现成**：字段**已经定义好了**，且前端属性面板**已经暴露**。所以这不是"设计新字段"，是"**把已有声明接上执行**"——纯实现补全。
- **抄主流**：提供**默认值**（避免"不填就无限等"）。定 30s，与既有 HttpClient 超时一致。
- **避坑（本系统特有）**：包裹点必须是**唯一的节点分发函数** `ExecuteNodeAsync`（`:556`），而不是每个 `case` 内部——否则新增节点时必然漏包，重演"配了不生效"。这是**利用了本系统"单一分发点"这个既有优势**。
- **不抄**：不引入超时后的自动重试（超时重试 = 可能重复副作用，与 R1 的安全默认值矛盾）。超时就是失败，由 R6 幂等 + R7 续跑兜。

## R3　非 HTTP 写节点弹性：现有 vs 主流

| | 现有实现 | 主流参考 |
|---|---|---|
| DB/Redis/Mongo 写 | **无任何弹性**（不经过 HttpClient，R1 的全局策略覆盖不到） | n8n 的 DB 节点有重试开关；Temporal 用 Activity 重试 |
| 读 | 无重试 | 普遍允许自动重试 |

**取舍**：
- **抄主流**：**读写分离策略**——读可重试、写默认不重试。这是数据库访问的通用共识。
- **守现有**：**不新建四个执行器各自的重试**。抽一个 `INodeResiliencePolicy`，四个执行器共用一份策略。
- **不抄（重要）**：不实现"写重试 + 自动补偿"这种 Saga 完整形态。理由：补偿链需要每个节点声明逆操作，属**重大架构投入**；而本系统 90% 的批量写场景可由 R4 的**单节点事务**覆盖（原子性在节点内解决，不需要跨节点补偿）。
- **依赖**：写重试若开启，**强制要求幂等键**（R6），否则校验报错——这是把"纪律"落进代码而不是文档里。

## R4　批量 CRUD：现有 vs 主流

| | 现有实现 | 主流参考 |
|---|---|---|
| SQL 批量 | **`ParameterizedSqlExecutor.BatchAsync` 已存在**：单连接 + `BeginTransactionAsync` + 逐条 + 失败回滚 + 500 行上限（`:113-175`） | NocoBase/Amis 的批量接口；Supabase 的 RPC 批处理 |
| 资源 CRUD | `ResourceCrudExecutor` **只有单条** `CreateAsync`/`UpdateAsync`/`DeleteAsync` | 均提供批量 |
| 前端 | 有 `batchDelete` 动作（`batchLimit: 100`），但**内部 `for` 逐条调**（`runtime.vue:511`） | 单次批量请求 |
| Code 节点 | `db.batch` **已暴露**（`CodeSandboxExecutor.cs:240`） | — |

**取舍（本轮最重要的一个判断）**：
- **复用优先，这是纯"接线"**：事务机制、参数化、行数上限、回滚**全部已存在**于 `BatchAsync`。R4 只需让 `ResourceCrudExecutor` 把多条数据**拼成 `paramList` 交给 `BatchAsync`**，而不是自己写事务。
- **抄主流**：批量接口返回**部分成功**结构（`succeeded` / `failed[{index,error}]`），与 R4 的 ForEach 输出契约、Parallel 输出契约**保持一致形状**——这是本系统已有的输出设计习惯（`{ items[], count, succeeded, failed[] }`），延续它比引入新形状更好。
- **避坑**：`stopOnError` 语义。`BatchAsync` 是"一失败全回滚"，这是**事务的正确语义**；若要"跳过失败继续"，就**不能**用一个事务包——两者矛盾。轻量化做法：**先只提供全事务语义**（`stopOnError: true` 即唯一形态），"跳过失败"留给 ForEach + `itemErrorMode: continueOnError`（已有能力）。**不重复造轮子**。
- **避坑（MongoDB）**：`BatchAsync` 只在 SQL 家族；Mongo 无跨文档事务。**明确标注**而非假装支持。
- **不抄**：不在资源记录 API（`/delete`）层新建批量端点后就丢掉原有的流程链——记录删除**走的是资源的 `DeleteFlowKey` 流程**（`AppResourceAppService.cs:135`），即"删除"本身是可被编排的逻辑，不能绕过去直接 DELETE 表。批量版必须**仍是调流程**，只是把 N 次调用收成 1 次。

> **R4 的真正难点不是事务，是"批量也要走流程"**。如果图省事直接批量打表，就把"删除逻辑可编排"这个既有优势丢了——那是倒退。

## 与既有优势的冲突检查（每项都要过一遍）

| 优势（方案 §0 约束） | R1 | R2 | R3 | R4 |
|---|:---:|:---:|:---:|:---:|
| 出参必过 `FinalOutputAssembler` | — | — | ✅ 不影响 | ✅ 输出走既有装配 |
| 新字段必加 `ValidateDsl` 校验 | — | ✅ 加 timeout 校验 | ✅ 加 retryOnWrite 校验 | ✅ 加批量上限校验 |
| 不引入第二套执行循环 | — | ✅ 包裹 `ExecuteNodeAsync` | ✅ 装饰而非替换 | ✅ 复用 `BatchAsync` |
| 前端只落 `graphJson` | — | ✅ 面板已有字段 | ✅ 新增开关 | ✅ 批量动作已存在 |
| 导出只导引用清单 | — | — | — | ✅ **批量仍调流程，未内联** |

**结论：四项均不与既有优势冲突，且 R1/R2/R4 都是"接已有线"，不是"造新东西"。**

## 轻量化实现清单（最终确定的范围）

| 项 | 改动性质 | 触碰文件数（预估） | 新增 DSL 字段 |
|---|---|:---:|:---:|
| R1 | 改 2 处配置 | 2 | ❌ 无 |
| R2 | 加 1 个包裹函数 + 校验 | 2~3 | ❌ 无（字段已存在） |
| R3 | 加 1 个策略类 + 接线 | 2~3 | ⚠️ 仅 `retryOnWrite`（可选） |
| R4 | 加 3 个 op + 1 个批量 API | 4~5 | ❌ 无（复用 `op`） |

**四项合计不新增任何必需 DSL 结构**，因此前端改动被压到最小（R2 面板已有、R4 批量动作已有、R1/R3 基本纯后端）。
