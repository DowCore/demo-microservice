# OA 人审

另一套引擎。对标钉钉和飞书的审批模板：一个流程一张表单，纵向节点配置办理人、会签和条件。不对标 Flowable / Camunda 的 BPMN 运行时。编排画布里不画审批人，审批引擎里不写 SQL。

证据在 [审批流契约](./detail/oa-contract.md) §2、§4、§5。基线 `267d375`。

## 已实现

- 节点：start / approver / cc / condition / end。新建定义直接是 `nodes` / `edges`。
- 办理人：用户、发起人、角色、表单字段、组织树主管、另一条 flow。空办理人默认报错。
- 多人规则：single / all / any / sequential / ratio。
- 动作：通过、驳回终止、驳回到发起人、驳回到上一节点、转办。抄送走 RabbitMQ，失败不阻断。
- 启动时固化流程 JSON。发布前校验类型、出线、无环、办理人和条件优先级。未知节点类型会抛错。
- 算数和改数据通过节点前后的 flowKey，不在审批服务里写 SQL。

## 相对对标的不足

| 对标有的 | 本仓现状 |
|---|---|
| 驳回就是驳回 | 会签或比例节点上，驳回可能被记成同意并继续向下 |
| 已发布模板不可被悄悄改掉 | 已发布流程可以用 PUT 改稿且不再校验。删掉出线后，新实例可能无人审批就变成已通过 |
| 办理意见和改过的字段一定落库 | 部分驳回分支和中途抛错会丢掉本次补丁 |
| 并发只有一人成功 | 实例和待办没有乐观并发，双击可能推进两次 |
| 不能自己批自己的主管节点 | 主管解析不排除发起人本人 |
| 超时、催办、加签、撤回 | 都没有 |
| 并行分支和子流程 | 人审侧没有。编排里的 Parallel 不能当作审批汇合 |
| 条件与报表使用同一棵条件树 | 审批连线仍是编号加 `combine` 字符串 |

未在节点上声明的字段，办理人默认可以改。只存了表单版本号，没有那一版的结构快照。

## 后续规划

| 优先级 | 事项 |
|---|---|
| P0 | 驳回必须走驳回语义，不能落到同意。补丁在推进前落库。实例和待办加并发戳 |
| P0 | 已发布定义禁止原地改写；要改就回草稿或发新版本 |
| P0 | 主管解析排除发起人。发布校验改读表单已发布快照，而不是草稿字段 |
| P1 | 未声明字段默认只读。条件边的优先级和默认分支在发布时查重 |
| P1 | 超时与催办 |
| P2 | 加签、减签、撤回、发起人自选审批人 |
| P2 | 审批条件迁到与报表相同的条件树 |
| P3 | 人审侧的并行网关和子流程。只有「单链加条件」不够用时才评估 Elsa / Flowable |

明确不做：把审批节点放进逻辑编排；一个流程绑多张主表单。
